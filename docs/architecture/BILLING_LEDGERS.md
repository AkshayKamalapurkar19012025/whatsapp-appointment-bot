# Billing Ledgers

## Purpose

Record, in one place, that this application has two independently-maintained billing tables for the same patient visit — not a documentation exaggeration, and not (yet) unified. Phase 9's source-of-truth audit named this precisely; this doc is the durable record of that finding and of Option C, the first phase of work against it.

## Current State

**Ledger A — appointment-level, the original mechanism** (migrations `0018`/`0019`/`0025`/`0026`):
- `appointments.payment_status` (`UNPAID`/`PAID`/`FAILED`/`WAIVED`/`REFUNDED`), `payment_method`, `payment_amount`, `payment_recorded_by/at`, `waive_reason`, `refund_amount`/`refund_reason`/`refunded_by/at`.
- `invoice_line_items` — ad-hoc extra charges on top of the consultation fee, frozen once `payment_status` leaves `UNPAID`/`FAILED`.
- Amount charged = `doctor_appointment_types.consultation_fee` + `SUM(invoice_line_items.amount)` (`get_invoice_service`, `app/services/appointment_services.py`).
- Covers: the consultation/registration fee only. Never lab, radiology, procedure, pharmacy, or package charges.
- **Drives queue-token issuance.** `generate_queue_token_service` is only ever called from `record_payment_service`'s `PAID` outcome, `waive_consultation_fee_service`, and `settle_free_visit_service`, and only while the appointment is still `CHECKED_IN` — all three read/write this ledger exclusively, under a `pg_advisory_xact_lock` + row `FOR UPDATE`. This is the single most concurrency-sensitive write path in the app.
- **Payment is collectible while `status` is `CHECKED_IN` or `COMPLETED`** (`_lock_appointment_for_payment`). Originally `CHECKED_IN`-only — a visit that closed with its consultation fee still unpaid was stuck that way permanently, with no API path to record, waive, or settle it (`tests/test_exception_engine.py::test_payment_pending_exception_from_unpaid_consultation_fee_alone` used to assert the 409 this produced). **Fixed**: `_lock_appointment_for_payment` now also accepts `COMPLETED`; none of the three actions issues a queue token in that case (there's no queue left to admit that patient to), only when still `CHECKED_IN`. The frontend already rendered the Record Payment/Waive form for this case regardless of appointment status (`AppointmentDetailsModal.tsx`'s `needsAction` only ever checked `payment_status`) — this closed a real, already-visible dead end.

**Ledger B — encounter-level, the newer model** (migration `0033`, widened by `0038`/`0039`/`0046`/`0050`):
- `invoices` (one per encounter) → `charges` (`source_type` = LAB/RADIOLOGY/PROCEDURE/SERVICE/PHARMACY/PACKAGE/CONSUMABLES/CONSULTATION/OTHER) → `payments`.
- Covers everything except the consultation fee in practice. `CONSULTATION` is a legal `charges.source_type` value, but nothing in the app ever auto-creates one — a billing clerk *could* manually add a charge and hand-pick `CONSULTATION`, creating an ad-hoc, unlinked duplicate of what Ledger A already tracks. Not currently prevented.
- Not gated on appointment status at all — a charge/payment can be recorded before, during, or well after the visit.

**No foreign key or trigger connects the two.** They are separately-maintained tables, not two views over the same data.

### Where each screen reads from

Superseded by a write-side change after Option C: a separate effort (`docs/architecture/BILLING_LEDGER_UNIFICATION.md`, "Phase 10", migrations `0058_billing_ledger_unification.sql`/`0059`) now records every real consultation-fee payment **directly** into Ledger B — a `CONSULTATION` charge + payment on the encounter's invoice, written by `billing_services.record_consultation_fee_payment_service`, linked back via `appointments.consultation_payment_id`. Not a mirror of a legacy-column write: for a payment recorded after Phase 10, `appointments.payment_status`/`payment_amount` are never written at all; Ledger B *is* the record. (An earlier, separately-developed attempt at this same goal — `migrations/0058_consultation_fee_ledger_mirror.sql`'s `mirror_consultation_*` dual-write layer, "ADR-009 Option B" in `docs/OPD_HIMS_ARCHITECTURE_AUDIT.md` — physically duplicated every payment into a second, `legacy_appointment_id`-tagged charge/payment row on top of this direct write. The two write paths collided on `charges_one_consultation_per_invoice` and crashed every real payment; the mirror was removed rather than reconciled, since the direct write already does everything it existed for. See that audit doc's Sixth Addendum for the full incident record.)

| Screen / endpoint | Reads |
|---|---|

### Secondary asymmetries (not addressed by Option C)

- **Refund semantics differ.** Ledger A: `record_refund_service` sets `payment_status = 'REFUNDED'` unconditionally, even for a partial refund, and refuses a second refund attempt outright. Ledger B: `payments.refunded_amount` is a running numeric total on a payment that stays `COMPLETED`, supporting incremental partial refunds. Unifying the ledgers means picking one of these two models.
- **`FAILED`/`DECLINED`** exist on both (Ledger A since `0018`; Ledger B added `DECLINED` in `0050`, explicitly modeled to mirror Ledger A's `FAILED`), but `AppointmentBillingPanel.tsx` doesn't yet expose the `DECLINED` outcome in its UI (API-only today).
- **A `CONSULTATION`-sourced charge is possible but never auto-created** — see above. Latent double-counting risk if a billing clerk ever manually adds one.

## Target State

The audit named three options; none of them is exactly what happened next, so the naming needs reconciling rather than treated as settled:

- **Option A (this doc's original naming) — Ledger B absorbs Ledger A entirely.** This is, in substance, what `docs/architecture/BILLING_LEDGER_UNIFICATION.md`'s "Phase 10" actually built for the payment-collection write path: a real consultation-fee payment is now written directly into Ledger B (`charges`/`payments`, `source_type = 'CONSULTATION'`), linked back via `appointments.consultation_payment_id`; the legacy `payment_status`/`payment_amount` columns are never written again for that case. Ledger A is retained only as the permanent record for waivers (never representable in Ledger B — `charges.amount`/`payments.amount` both `CHECK (amount > 0)`) and as a historical-compatible column set for pre-Phase-10 data. Token issuance (`generate_queue_token_service`) was preserved exactly, untouched — the token-issuance risk this doc originally flagged for a full Option A didn't materialize, since the trigger condition (`outcome == 'PAID'`) never moved.
- **Option B (this doc's original naming) — Ledger A absorbs Ledger B.** Not what was built.
- **A separately-developed, since-removed third attempt** (`migrations/0058_consultation_fee_ledger_mirror.sql`, tracked in `docs/OPD_HIMS_ARCHITECTURE_AUDIT.md` as "ADR-009 Option B" — a name that collides with, but means something different from, this doc's own Option B): a dual-write mirror, physically duplicating every Ledger A payment into a second Ledger B row. Built and reconciled against Option C before Phase 10 existed; superseded by Phase 10's direct write, which does everything the mirror existed for without a second write path. The two coexisting uncoordinated became a real, already-merged crash (every real consultation payment hit `UniqueViolation` on `charges_one_consultation_per_invoice`) — removed rather than reconciled. See that audit doc's Sixth Addendum for the incident record.
- **Option C (this doc's read-only merge)** — done, and still the mechanism `GET /dashboard/billing` and the Exception Engine's `PAYMENT_PENDING` use: `_ledger_b_collections_by_method/_by_doctor/_outstanding` (dashboard) and `_payment_pending` (exception engine) exclude whatever Ledger A's own `EFFECTIVE_PAYMENT_*_SQL`-based query already covers (a `consultation_payment_id`-linked payment, a `CONSULTATION`-sourced charge), since without that exclusion a real payment would be counted once via the `EFFECTIVE_PAYMENT_*_SQL` fragment and again via an unfiltered Ledger B query — a real double-counting bug, caught the same way the mirror-crash was (reproducing a test failure against a clean `main` before assuming a change of one's own caused it) and fixed alongside removing the mirror.

## Gap

- **Billing History / Payment History** — Ledger B only, still not addressed by Option C directly, but now shows the consultation fee anyway as a side effect of Phase 10's direct write — the row-shape design question this doc originally raised turned out not to need answering.
- ~~A visit closed with its consultation fee still unpaid is visible but not collectible~~ — **fixed**. `_lock_appointment_for_payment` (`app/services/appointment_services.py`) now accepts `COMPLETED` as well as `CHECKED_IN`; `record_payment_service`/`waive_consultation_fee_service`/`settle_free_visit_service` all work on a `COMPLETED` appointment, none of them issues a queue token in that case. See `tests/test_consultation_payments.py` for the new coverage.
- ~~Every real, non-zero consultation payment crashed~~ — **fixed**. A separately-developed dual-write mirror (`mirror_consultation_payment` et al.) was still being called alongside Phase 10's own direct write, and both tried to create the same `ACTIVE` `CONSULTATION` charge on the same invoice — `charges_one_consultation_per_invoice` correctly rejected the second insert as an uncaught `UniqueViolation`. The mirror was removed (see Target State above); `record_payment_service`/`waive_consultation_fee_service`/`record_refund_service` now have exactly one Ledger B write path each.
- ~~`GET /dashboard/billing` double-counted every real consultation payment, and `PAYMENT_PENDING` never cleared for one~~ — **fixed**, found in the same investigation as the crash above. Both endpoints' Ledger B exclusion filters were written against the (now-removed) mirror's `legacy_appointment_id` tag, which Phase 10's direct write never sets — so the filter never excluded it, and `_payment_pending`'s own Ledger A query separately still read the raw, permanently-stale `payment_status` column. Both switched to the actual current linkage: exclude via `consultation_payment_id`/`source_type = 'CONSULTATION'` on the Ledger B side, `EFFECTIVE_PAYMENT_STATUS_SQL` on the Ledger A side.
- **`CONSULTATION`-sourced charge double-counting** — still a latent risk for any *manually* added `CONSULTATION` charge (one never created by `consultation_payment_id`'s own linkage). Now excluded from Ledger B's own totals by the `source_type != 'CONSULTATION'` filter above, but since it's also never linked from any appointment, it would be invisible to both ledgers' reports rather than double-counted — an improvement in kind, not a fix; no code path creates one today. Not addressed further by any of this work.
- The naming collision between this doc's Option A/B/C and `docs/OPD_HIMS_ARCHITECTURE_AUDIT.md`'s different "ADR-009 Option B" lettering is now moot for the write path (that option was removed), but the audit doc itself remains a historical record using its own original lettering — a reader consulting it for history should be aware the terms don't map onto this doc's.

## Recommended Implementation

Done for this pass: the `COMPLETED`-appointment payment gap, the mirror-collision crash, and the resulting double-counting/never-clearing read-side bugs. What's left is lower-priority: decide whether a manually-added `CONSULTATION`-sourced charge should be prevented outright at the DB layer (or explicitly supported and linked), rather than silently excluded from every report as it is today.
